# Catalog 반복 조회의 DB 작업 줄이기

## 업무 요청

같은 상품 목록을 반복 방문할 때 DB 작업이 크게 줄어야 합니다.
조회 비용을 줄이더라도 고객이 보는 상품·가격·재고 정보가 잘못되면 안 됩니다.

## Pair 시작 질문

> 같은 상품 목록을 반복해서 조회할 때 DB 작업을 줄이고 싶어.
> 현재 동작을 같이 살펴보면서 어디부터 접근할지 이야기해 보자.
> 아직 구현 방법은 정하지 않았어.

## 빠른 시작

Repository 루트에서 `MARKETLANE_DB=.data/catalog-cache.sqlite npm run dev`를 실행합니다.
main의 기본 DB나 다른 과제의 DB를 공유하지 마세요.
브랜치 전환·초기화 전에 서버를 중지합니다. 필요할 때만 초기화하세요:
`MARKETLANE_DB=.data/catalog-cache.sqlite npm run db:reset -- --confirm`

## 수용 기준

1. 같은 데이터와 같은 조회 순서로 비교했을 때 반복 조회의 DB 작업이 변경 전보다
   줄어듭니다. 비교할 작업량과 감소 목표는 구현 전에 사용자와 정하고, 재현 가능한
   결과를 남깁니다. 처음 준비하거나 변경을 반영하는 비용도 함께 드러냅니다.
2. 한국어·영어, 번역 fallback, 검색, 분류, 정렬, 페이지 이동, 재고 필터의 기존
   결과를 유지합니다. 서로 다른 조회 조건의 상품이나 개수가 섞이지 않습니다.
3. 운영자의 상품 수정이 성공한 뒤 시작한 목록·상세 조회에는 수정한 내용이 보입니다.
   수정 때문에 달라진 검색 결과와 정렬 순서도 반영하며 실패한 수정은 노출하지 않습니다.
4. 주문 접수나 재고 조정이 성공한 뒤 시작한 조회에는 현재 재고가 보입니다.
   품절 여부뿐 아니라 재고 필터의 목록, 전체 개수와 페이지 내용도 맞아야 합니다.
5. 견적과 주문은 현재 가격·재고를 기준으로 처리합니다. 초과 판매나 실패한 주문의
   일부 반영이 생기지 않으며, 서버 재시작 후에도 기존 상품·주문·재고를 읽을 수 있습니다.

## 범위

상품 목록 조회 개선만 다룹니다. 기존 가격 규칙, 주문 처리, 페이지 탐색과 브라우저
장바구니의 의미를 바꾸거나 재고 예약을 추가하지 않습니다. 기술, 데이터 구조,
조회 결과의 재사용 여부와 변경 반영 방식은 정하지 않습니다.
